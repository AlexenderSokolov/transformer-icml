## Preservation contract

The candidate generator executes precisely the original order: n-by-4 transition probabilities, n integer initial pairs, then 64 successive n-vectors of independent uniforms. Before each candidate batch consumes randomness, an immutable intent records its set, batch index, size, horizon and prior PRNG state and is fsynced. An intent with no completed batch file marks an uncertain, uncommitted batch; the intent does not preserve any values already generated in RAM. There is no automatic replay or repair. Reconstruction would require a compatible environment and separate authorization. Every committed candidate batch is atomically persisted and fsynced before its selected words are used, including all rejected and overshoot candidates, exact probabilities, starts, all 64 by n uniforms, generated words, eligibility and final selection flags, generation order, and before/after NumPy bit-generator states. This includes unconditioned natural evaluation. Frozen selected data and the full minibatch index stream, with its before/after PRNG states, are atomically persisted before fitting. Before applying each optimizer update, the program calculates its proposed next state on copies and appends a durable, length-framed, SHA-256-protected write-ahead record containing all 353 gradient values and all 353 resulting parameter values, plus arm, seed, step, names, shapes, float format and flatten order. Then it commits those copies in memory and records the norms CSV row. A complete, fsynced final journal record can represent a prepared update that had not yet been applied to the live model or evaluated. A record alone is not proof of application or evaluation. An interrupted CSV write can also leave a partial terminal line; checkpoint state and logs must be reconciled rather than inferring commitment from journal presence. Check journal integrity with `python validate_update_journal.py OUTPUT/full_updates.bin`; this prefix check can pass for an empty or incomplete journal. Add `--complete` to require exactly six expected arm/seed sequences of 2,000 consecutive records each, 12,000 total. A partial header or payload, checksum mismatch, invalid schema or nonconsecutive step is an error in either mode. A complete journal count describes prepared records, not proof that every corresponding update was applied or evaluated. Before claiming the experiment completed, independently reconcile all 12,000 update-summary CSV rows, each final checkpoint and its optimizer step/state, checkpoint and final metrics, results, and the full console log with the journal and expected six fits; investigate any missing or contradictory evidence. Never silently discard or repair an incomplete record. The checkpoint-metric and update-summary CSV rows are individually flushed and fsynced. Each checkpoint atomically stores model parameters, condition and scale, all Adam first and second moments, optimizer step and hyperparameters. These checkpoints permit state reconstruction but the runner does not implement automated restart; investigate any interrupted run rather than silently resuming or modifying protocol. Exact bitwise replay across different NumPy/BLAS/platform versions is not promised; preserve and report environment versions.

Run only after independent approval and sealing. Use the approved launcher from this directory: `python launch_exclusive.py --log confirmation_console.log --output confirmation_v1`. It atomically creates the console log with O_CREAT|O_EXCL, so an existing log cannot be truncated, then redirects both stdout and stderr to that descriptor and execs unbuffered Python. The runner checks that both descriptors refer to the same empty regular file and that the launcher indicator is set; this indicator is not a security boundary and direct invocation is prohibited by this protocol. Keep the console log with the outputs and hash it separately after process termination. The script fsyncs its own console messages, but an abrupt system failure can still lose interpreter error text emitted after the last sync. New output directory ancestors are created and fsynced, and final metadata and CSV files use fsynced temporary files plus exclusive hard-link publication and directory fsync. Durability depends on filesystem and storage honoring these semantics.
