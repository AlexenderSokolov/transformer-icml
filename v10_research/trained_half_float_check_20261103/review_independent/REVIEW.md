# Independent review: saved half-checkpoint float check

3 November 2026. Reviewed the deterministic checkpoint check, current saved results and report. This audit uses two fixed words and existing weights; it performs no random operation, `Model.__init__`, model fitting or stochastic sampling. The observed results reproduce in the stated environment. They concern one existing checkpoint and one chosen pair, not uniform bank sufficiency or global maximization.

## Checkpoint, inputs and numerical path

The loaded checkpoint is the original `smoke_v1/checkpoints/half_edit_200.npz`, SHA-256 `bc95b1e2f5dc4361224a4b52b740263bdda74242a81eaa52e49584020a22b848`, matching the smoke artifact manifest and saved result binding. Its mode is `half`; its finite saved arrays have the expected a, W, b, v and c shapes. The audit allocates `pilot.Model` with `__new__`, explicitly blocks its random-initializing constructor, and assigns those saved arrays directly. The unused a array remains present as in the original model; fixed half pools are generated from M, not from learned weights.

At M=1025, clean A has zeros at 515 and 518, B at 519 and 522, with all other bits one. Direct Python-integer triple counts give the same protected terminal pair 11 and bank (J,C1,D,E)=(1021,1019,512,512). Four differing indices lie in the editable prefix, so both identity A and B are legal from A with k=4. Their exact rational input vector is (2/1025,1019/1025,0,1,2/513,507/513,1,1,1/1025); clean B(A)=340/341.

A separate literal triple pipeline and the actual saved-checkpoint `pilot.Model.forward` agree bitwise for x, hidden values, sigmoid, q and CE on AB, BA, AA, BB and each singleton batch. The independent pipeline deliberately uses the same NumPy einsum and matrix kernels to test the specified executable semantics; it is not an independent backend implementation or a proof of floating reduction behavior. The log records Python 3.12.14, NumPy 2.3.5, mpmath 1.3.0, scipy-OpenBLAS 0.3.30, platform and thread settings (OPENBLAS_NUM_THREADS=1, OMP_NUM_THREADS=1, MKL_NUM_THREADS unset).

## Results and interpretation

In the two-row batches, A and B's successor-one pooling rails differ by one ULP and follow the words when their order is swapped. For these particular saved weights, however, their final logits are identical (`0x1.3a0db665792cbp+2`), as are q (`0x1.fc3dd84f48330p-1`, about 0.9926593395976848) and clean-target CE (`0x1.647a2c4900137p-6`, about 0.021757643935417206). AA and BB agree with the same two-row outputs. In singleton calls both logits shift upward by 18 binary64 ULPs (`0x1.3a0db665792ddp+2`), while q and CE still round to the same binary64 values. This is a batch-layout-dependent logit, not an observed output or CE separation for this checkpoint/pair.

Independently recomputing the ideal rational input with the exact real values represented by the saved binary64 weights at 120 mpmath decimal digits agrees with the author's 100-digit logit, q and CE to better than 1e-88. The estimated absolute logit differences from that high-precision reference are about 1.0551e-15 for the two-row calls and 1.7043e-14 for singleton calls. Both happen to be below the previously reported 1.1746381927788e-12 conditional tau_h=0 logit component. The high-precision values are approximations, not interval-certified exact reals; this comparison does not verify NumPy's reduction graph, uniform tanh/sigmoid/log errors, the complete conditional error bound, or an argmax.

The earlier deliberately amplified readout still proves a same-bank, same-batch executable output separation in this environment. This new saved-checkpoint observation neither retracts that counterexample nor proves that the saved model's count bank determines floating outputs for other words, checkpoints, layouts, horizons or backends. M=1025 was not a training/evaluation horizon in the original smoke. No attack-set global maximum or robustness conclusion follows.

## Provenance and preservation

All four entries in the author's current SHA256SUMS and all seven source bindings embedded in `trained_results.json` match. The independent script and its full environment/result log are retained in this review directory; it does not overwrite author results. The independent numerical pipeline shares the specified NumPy/BLAS operations as noted above, while the high-precision reference uses separate mpmath arithmetic.

During this review, I observed `check_trained.py` change from 6,227 to 6,336 bytes and `check_trained.log` from 1,911 to 5,096 bytes; the saved `trained_results.json` was also written again. Earlier versions were not found as separately named artifacts in this directory, and their full bytes and hashes were not captured by this audit. The current manifest binds the final versions only; it should not be described as preserving all intermediate output. This observation alone does not establish whether every earlier and final JSON field differed. The author has since confirmed the overwrite in `PRESERVATION_CORRECTION.md`: the initial script, log and full JSON were replaced when NumPy/BLAS configuration reporting was added, with no separately preserved first-run artifacts or first-run hashes. The six concise initial numerical lines visible to this audit agree with the retained rerun; the unprinted initial JSON cannot be compared. All six entries in the separate `PRESERVATION_BINDINGS.sha256` match. The correction does not recreate the missing originals.
