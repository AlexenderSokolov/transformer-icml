# Deterministic floating-point bank audit

2026-11-03. This is an environment-specific numerical investigation, not a trained-model experiment, a novelty claim, or a real-number optimality certificate. No random number generation or random model initialization was performed. Frozen files were read only, and this folder is additive.

## Fixed-shape counterexample

For M=1025, let A and B each have 1027 bits, all 1 except zero-based positions {515,518} in A and {519,522} in B. Their endpoint is (1,1), their Hamming distance is 4, and both banks (J,C1,D,E) equal (1021,1019,512,512). Evaluate both together in a two-word, C-contiguous int8 batch by the actual `pilot.Model.forward` half-pooling path, with NumPy 2.3.5 and OpenBLAS 0.3.30, with `OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1` set before Python starts. The first (uniform) successor-1 features are respectively:

- A: `0x1.fd00bfd00bfd6p-1`
- B: `0x1.fd00bfd00bfd7p-1`

Swapping batch rows swaps these outputs with the words. This demonstrates that these counters do not, in general, determine the bitwise floating features for this actual invocation. It does not show that any trained pilot readout separates the words, nor that this particular example witnesses an incorrect global maximum.

To show the discrepancy can matter for the actual neural architecture, the deterministic reproduction constructs a Model with `__new__` (no constructor or RNG call). With all other parameters zero, set W[1,0]=2^53, b[0]=−2^53 × float.fromhex('0x1.fd00bfd00bfd6p-1'), and v[0]=1. This intentionally amplifies a one-ULP feature discrepancy and is not a trained checkpoint. The forward outputs are A=0.5, B=0.6816993976515352. With A as clean input and the usual target B(A)=0.9970674486803519, CE is respectively 0.6931471805599453 and 0.38539989350195286. Both candidates are reachable from A with edit budget k=4, and the protected terminal is unchanged. This establishes that the counter equivalence class is not always utility-equivalent for even a fixed supported readout and the pilot CE, so dominance based solely on the count bank is unjustified in general. It does not by itself establish what the global maximizing candidate is.

Run from repository root:

`OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python v10_research/float_bank_deterministic_20261103/fixed_shape_verify.py`

`fixed_shape_verify.log` records A/B, B/A, A/A, B/B, complete feature hex strings, predictions, target, losses, Python, NumPy, CPU feature flags and BLAS configuration. `fixed_batch_search.py` and `.log` record how the example was deterministically found; the search uses the same batch size within each sweep and is a location sweep, not an exhaustive search of all words. The counterexample was independently re-evaluated by the reproduction script.

## Current reconstruction does not match the float implementation

At M=5, word 0011111 gives bank (3,3,0,0). In an exhaustive 128-word batch, actual NumPy feature 1 is `0x1.3333333333334p-1`, while `model_inputs` produces `0x1.3333333333333p-1` from 3/5. Thus merely evaluating one count-reconstructed float input per bank does not reproduce the actual model even before the bank collision issue. `check_reconstruction.py` and `reconstruction.log` are deterministic and log the first mismatch, after exhaustive searches of all words at M=2,3,4 and the word prefix at M=5.

## Batch shape and scope

Floating reductions are not mathematically associative and NumPy's optimized einsum can select different BLAS kernels/reduction orders by shape, backend and platform. For the same M=257 input, the uniform successor-1 feature is `0x1.f40bf40bf40a4p-1` in the tested 1024-row batch and `0x1.f40bf40bf40c0p-1` in the tested 16-row batch. `reproduce_collision.py`/`.log` document this and same-slot comparisons. The initial `structured_search.py` stopped at a difference across batches of different sizes, so `structured.log` is NOT evidence of a fixed-shape word collision. The fixed-shape collision is the separate M=1025 example above. Exact numbers and collision locations are environment-dependent, and no claim is made that all BLAS implementations behave alike.

`find_collision.py`/`search.log` exhaustively cover all 2^(M+2) words per M=2..20 in batches of 2048 (or the full set if smaller). They found no feature collision under that search, but this is a finite observation, not a proof. `structured_search.py` uses all-0 or all-1 baselines with <=2 editable flips and all four terminals, ordered deterministically; it terminated upon the across-batch difference described above. No transient model initializations or random samples were used.

## A systematic exact-float fallback and cost

A fully general fallback is to enumerate each legal edit mask on the M editable positions with weight <=k, evaluate the **actual specified** float implementation, and compare its returned floating CE values using a specified rule for ties, infinities and NaNs. There are N=Σ_{j=0}^k binom(M,j) masks. This is source-blind when target and weights are legitimate fixed public inputs, and guarantees the maximum of that finite set of computed float values, not the maximum of ideal real or exact-transcendental values. This does not rely on bank sufficiency. The evaluation protocol must specify batch size, layout, candidate order, slot, dtype, BLAS/version/threading and fixed weights: because shape changes results, a singleton evaluation cannot automatically be substituted for a batched implementation.

One unambiguous protocol is to put each candidate in the same designated slot of a fixed-size B batch with fixed filler words and evaluate the complete fixed batch for each mask. Provided repeated runs of the chosen backend are deterministic, its selected objective is defined exactly by this executable protocol. With the pilot's fixed 9×32 readout and 3 pooling heads, runtime is O(N B M) plus the N batched readout, transcendental, and comparison costs; workspace is O(B M) plus weights and O(M) mask/witness storage. Retaining a maximizing witness requires O(M) further bits. This deliberately specified protocol is not asserted to give bit-identical results to another batch layout. Alternatively create all N candidates in the exact intended batch order, call forward with that full batch and select its maximum: it needs O(N M) input/intermediate storage and O(N M) arithmetic, plus N fixed-size readouts, transcendentals and comparisons; it directly matches only that specified all-candidate invocation. Actual library allocation, tiling, startup and cache costs are additional; allocation or backend limits can make it infeasible. The deterministic bounded-k mask generation and actual learned checkpoint application are not implemented or run here.

A potentially smaller exact DP requires a proven backend-specific online reduction state. If, for fixed batch layout/slot and environment, one proves that its reduction can be simulated left-to-right by r binary64 accumulators plus fixed per-layer metadata, then retain window and the complete accumulator bit patterns in the DP key, along with any extra circuit state needed to make every continuation identical. At a layer there are at most S=min(2^(M+2),2^(64r)) accumulator patterns (a tighter bound requires analysis), and at most 4S two-bit windows; under an O(r)-cost verified transition the bound is O(M r S) arithmetic and O(r S) rolling storage, up to constant factors for window states and bit widths. Saving all predecessor layers costs O(M S) records, with metadata for transitions, and final readout scores add O(S) evaluations. The count bank can be retained too but must be included in the state bound unless derivable from accumulator state; counting explicitly gives a factor at most (M+1)^4, or one may bound the whole state by the number of input prefixes. Arbitrary backend reduction graphs may not admit a fixed small streaming state: split reductions, partial sums, fused operations and non-prefix order require their actual live circuit state, potentially O(M), and the resulting algorithm can be exponential. A proof of equivalence and concrete backend instrumentation are necessary before claiming this replacement computes the pilot path bitwise. No such polynomial exact-float DP is proved here.

## Corrections during this audit

The first version of `check_reconstruction.py` failed while serializing NumPy int8 counters to JSON; it was corrected to serialize integer values and rerun, with the successful run retained. An initial version of `reproduce_collision.py` also passed an int8 NumPy row directly to `feature_bank`, causing int8 overflow in its printed large counts; it was corrected to convert each bit to a Python int before counting. Those transient failed/superseded outputs were not saved as separate log files and are not represented as contemporaneous records; the final script and log above are the corrected rerun. The 257 structured search's differing batch sizes and the initial mistaken interpretation are explicitly identified above.
